# Dependency security review

Checked against main `cba6095` on 2026-10-24. GitHub had 16 open Dependabot alerts (6 high, 8 medium, 2 low); a fresh `pnpm audit --json` independently reported the same 16 advisory/version findings. The updated lockfile reports 0 known advisories. This is a dependency-advisory result, not a claim that all application or vendored code has been security audited. GitHub evaluates the default branch: alert closure is tracked separately from the audit result, and no alerts are dismissed.

## Findings and treatment

All 16 GitHub alerts label their manifest scope as development because this repository declares Electron and its build tools under devDependencies. That label alone does not determine runtime exposure: Electron is the shipped runtime, and electron-store/AJV code is bundled into main.

## Dependency paths and actual use

- `electron -> @electron/get@5 -> undici@7`: Electron binary installation/download. `electron-builder -> app-builder-lib -> @electron/rebuild -> node-gyp -> undici@6`: native rebuild/download tooling. The scoped overrides do not replace Electron's embedded Node/Chromium dependencies.
- `electron-store -> conf -> AJV -> fast-uri` is bundled main-process schema/config parsing; build loaders and app-builder-lib also use AJV. External links use the built-in URL parser and a separate validated policy, not fast-uri.
- Before migration: `@rspack/cli -> @rspack/dev-server@1 -> webpack-dev-server -> express -> body-parser`, plus launch-editor. These serve development only. The replacement dev server's vendored editor implementation is removed by the pinned package patch, and its endpoint remains explicitly disabled; opening a source file in a local editor from the browser is unavailable, while page serving and HMR remain available.
- `electron-builder -> app-builder-lib -> @electron/get@3 -> got@11 -> cacheable-request -> http-cache-semantics`: packaging-time download tooling. The advisory describes reuse across users in a shared HTTP cache; the application does not expose such a shared caching proxy. The 4.3.0 override remains within got/cacheable-request's compatible 4.x range.

## Coverage and remaining limits

`pnpm audit` is not GitHub code scanning or secret scanning. The code-scanning API returned `404: no analysis found`; secret scanning is disabled on this repository. No scanner settings were changed, no secrets were displayed, and no credentials were rotated. Existing deprecated dependency notices are not suppressed and were not used as a reason for unrelated major upgrades.

The existing follow-redirects 1.16.1 security override remains intact. The lockfile was updated normally, not deleted. The isolated update regression downloads a fixture ZIP from loopback HTTP and validates progress, checksum, errors and cancellation; it never invokes native installation. Signed installers, production-feed update downloads/installation, and exploit reproduction against real external services are outside this verification. See the [test coverage and boundaries](testing.md). Rsdoctor duplicate-package and intentional environment-side-effect diagnostics are build-analysis warnings, not the dependency advisories above.

## GitHub alert reconciliation and refresh

During the follow-up reconciliation, all 16 then-open alerts referenced the same `pnpm-lock.yaml`, not a second manifest. Main `697629f` and the exported GitHub SBOM agree on Electron 44.9.3, Undici 6.29.1/7.30.1, fast-uri 3.1.9 and http-cache-semantics 4.3.0; body-parser and standalone launch-editor are absent. The alert records still reference the previous versions. Twelve findings have patched/removed dependencies, three require accounting for the vendored editor (now removed by this patch), and the cache advisory remains the range-resolution/disputed case above. An up-to-date SBOM alone does not prove alert closure.

The official **Refresh Dependabot alerts** action was submitted through the authorized Mac Chrome session on 2026-10-24. GitHub displayed **Refresh queued, it may take several minutes to see changes reflected in your alerts**. This confirms queuing, not completion. No alert was dismissed and no security settings or credentials were changed. See [GitHub's dependency graph troubleshooting](https://docs.github.com/en/code-security/reference/supply-chain-security/troubleshoot-dependabot/dependency-graph-errors) for the official refresh path and hourly limit. If records remain inconsistent after processing, report the main lockfile/SBOM/alert evidence to GitHub rather than claiming an unobserved cause or suppressing alerts.
